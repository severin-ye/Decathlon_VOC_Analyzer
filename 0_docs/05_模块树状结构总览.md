## L1 大模块说明

### 05_src/decathlon_voc_analyzer/ —— 核心源码包

这是整个系统的 Python 包，包含全部业务逻辑。包下按职责分为 API 应用层、评估模块、LLM 网关、提示词层、Schema 数据模型、四个 Pipeline Stage（数据集标准化→评论建模→多模态检索→报告生成）以及工作流编排。此外还有独立文件的运行时进度上报器。所有模块通过 `get_settings()` 获取统一的配置中心，依赖关系清晰：Stage 后级引用前级产物，外部入口通过 workflows 和 scripts 调用服务层的 public API。支持多后端切换（远程 API / 本地 Qwen3 / OpenVINO）且通过运行时策略控制降级行为。

### 04_scripts/ —— 脚本入口层

提供所有面向用户的 CLI 入口和辅助脚本。核心入口 `run_workflow.py` 支持单产品 Pipeline 端到端执行并输出 JSON/HTML/RunManifest；`run_experiments.py` 控制实验矩阵的启动、停止和状态监控；`validate_multimodal_runtime.py` 用于验证多模态通道是否达到生成标准；`clear_generated_outputs.py` 安全清理产物目录。`launch_interactive_workflow.py` 用一个本地 HTTP 仪表盘交互式管理品类和产品的分析流程。此外还有模型下载、中文数据导出、HTML 报告导出等单步脚本，以及 `local_inference/` 下的本地推理和 OpenVINO benchmark 辅助。脚本不直接承载重业务逻辑，而是参数化地调用核心包的服务接口。

### 06_tests/ —— 测试体系

测试覆盖所有核心服务、API 端点、工作流和脚本入口。`conftest.py` 是 pytest 全局配置，通过 fixture 注入隔离的配置环境（清空 API Key、重置缓存、替换后端为 hash/heuristic），确保测试不依赖真实模型或外部 API。每个服务模块都有对应的 `test_*.py`，API 路由也有单独的 API 级别的集成测试。实验运行器的断点恢复和 UI 服务器也有专项测试。整个测试套件非常扁平：一份测试文件对应一份被测模块，命名一致，可以直接定位。

### 03_configs/ —— 配置层

仅包含两个 JSON 文件：`review_sampling_profiles.json` 定义了 `problem_first`、`balanced`、`praise_first` 三种评分感知采样策略的各星级权重分配；`runtime_execution_policy.json` 控制 `allow_degradation`（是否允许降级 fallback）和 `full_power`（是否强制全能力模式）两个布尔开关。这些配置由 `runtime_policy.py` 读入并在 Pipeline 各处用于 "降级-报错" 决策分支。配置简洁，但影响范围贯穿整个系统的容错行为和实验可重复性。

### 0_docs/ —— 文档体系

包含三大部分：`01_设计文档/`（按架构层次组织的完整系统设计，从术语表、技术选型到可解释性评估和实施路线）；`02_技术文档/`（LangChain 落地笔记、多语言召回说明、推理/微调教程等实操导向内容）；`03_论文子模块文档/`（10 篇与源码模块一一对应的论文写作笔记，是撰写论文时回溯设计细节的主索引）。另有独立的 `04_实验运行指南.md` 覆盖实验矩阵、LLM-as-Judge 评估和断点续跑的策略说明。

### 论文_md形式/ —— 论文写作

存放论文草稿的 Markdown 源文件、参考文献、标题页以及导出脚本。论文将系统描述为一个可复现的学术制品，而非冻结的跨品类榜单，因此论文写作与代码产物的产出路径紧密对应。

### 项目基础设施

根目录的 `pyproject.toml` 通过 `package-dir = {"": "05_src"}` 将源码指向 `05_src/`，核心依赖包括 FastAPI、LangChain/LangGraph、openai、Pydantic v2、Pillow、torch/transformers、qdrant-client；可选的 `openvino` 和 `gpu` 组提供本地模型推理加速。`AGENTS.md` 是面向 AI 编码代理的最小入口说明，定义了虚拟环境路径、pytest/ruff 命令、作用域约定和走读文档的优先顺序。`README.md` 是完整项目入口，覆盖流水线总览、安装、快速启动、API、配置、实验和引用。

## L2 中模块 & L3 小模块说明

### 核心源码包内

---

### ▸ app/ — API 应用层

提供基于 FastAPI 的 Web API 入口，供前端 UI 或外部调用。`core/config.py` 通过 Pydantic Settings 从 `.env` 加载全部运行参数（模型名、路径、API Key、后端开关），并自带 `@lru_cache` 以避免重复实例化。`core/runtime_policy.py` 从 JSON 文件加载策略并将降级/全能力门控封装为可重用的 `RuntimeExecutionPolicy` 对象和检查函数。`api/main.py` 通过 FastAPI 工厂函数创建应用实例，挂载 `/api/v1/` 前缀的 4 组路由。每组路由是一个薄路由文件，解包请求体后委托给对应的 Service 类。

#### api/main.py — FastAPI 应用入口

构造 `create_app()` 工厂函数，调用 `FastAPI()` 实例化并注册 4 个 API router（dataset/index/reviews/analysis）到 `/api/v1/` 路径前缀下。同时添加 `/health` 健康检查端点返回 `{"status": "ok"}` 和环境信息。允许 CORS 全来源方便本地开发的跨域 UI 访问。此文件不包含业务逻辑，纯粹是路由注册和生命周期管理。

#### api/routes/dataset.py — 数据集路由

定义 `GET /api/v1/dataset/overview`（目录扫描结果）和 `POST /api/v1/dataset/normalize`（触发标准化流程）两个端点。请求体解析为 Pydantic `DatasetNormalizeRequest` 后直接调用 `DatasetService.build_overview()` 和 `DatasetService.normalize_dataset()` 并返回 JSON。不超过 30 行，是纯粹的 API 适配层。

#### api/routes/index.py — 索引路由

定义 `GET /api/v1/index/overview`（查询索引状态）和 `POST /api/v1/index/build`（触发索引构建）。内部委托给 `IndexService.build_index()`。请求参数包括品类过滤、产品 ID 过滤、是否使用 LLM 嵌入等。本质上是 CLI 参数的 HTTP 版桥接器。

#### api/routes/reviews.py — 评论路由

定义 `POST /api/v1/reviews/extract`，接收商品 ID 和临时评论列表两种模式。前者从已标准化数据中加载评论执行 LLM 方面抽取，后者对即时传入的评论列表做抽取，适合 UI 试玩。调用 `ReviewExtractionService` 完成业务，返回方面列表和运行模式（LLM/heuristic）。

#### api/routes/analysis.py — 分析路由

定义 `POST /api/v1/analysis/product`，是 API 的最终出数端点。请求体包含商品标识、最大评论数、每方面问题数、是否跳过某些阶段等控制参数。委托给 `ProductAnalysisService.analyze_product()`，返回完整的 `ProductAnalysisResponse`（报告 JSON、检索记录、回放侧车、质量指标、配置快照等）。

#### core/config.py — 全局配置中心

用 Pydantic `BaseSettings` 从 `.env` 文件加载全部路径、模型名（qwen-plus / text-embedding-v4 / gte-rerank-v2 / qwen-vl-max-latest 等）、后端选择（api / local_qwen3 / clip 等）、API Key（Qwen / DeepSeek / OpenAI 三种）、本地 Qwen3 模型路径和设备选择。`get_settings()` 采用 `@lru_cache(maxsize=1)`，只实例化一次并自动创建全部产物目录。脚本或测试中修改环境变量后需清缓存才能读取新值。

#### core/runtime_policy.py — 运行时策略控制

从 `runtime_execution_policy.json` 加载 `allow_degradation` 和 `full_power` 两个布尔值封装为 Pydantic 模型，并提供 `get_runtime_execution_policy()`、`should_forbid_degradation()`、`resolve_llm_permission()`、`handle_llm_failure()` 等辅助函数。Pipeline 中任何需要降级（如 API 失败改用 heuristic）的位置都会先检查策略：若 `allow_degradation=false` 则抛出 `RuntimePolicyError` 阻断执行，确保正式实验中不会静默 fallback。`full_power=true` 还会额外校验 LLM 不可禁用且所有模型后端可用。

---

### ▸ evaluation/ — 评估模块

#### manifest_evaluation_service.py — Manifest 评估服务

读取单次运行产出的 `*_run_manifest.json` 文件，自动计算三类指标：(1) 检索质量，如有 gold label 则输出 Recall@k、MRR、NDCG，无 gold 时输出审计型统计（证据覆盖率、分数漂移、冲突风险）；(2) 报告质量，包括 claim 支持率（supported/partial/unsupported 分布）、citation precision（有产品证据支撑的引用比例）、证据路由贡献（文本/图片/混合各自占比）；(3) 工作流审计，包括有效评论数、aspect 数量/置信度、问题数量和置信度等。支持多 manifest 对比分析，是实验报告的主要数据来源。

---

### ▸ llm/ — LLM 网关

#### gateway.py — 统一 LLM 调用网关

封装为 `QwenChatGateway` 类，对外暴露唯一方法 `invoke_json(prompt_template, variables, schema, temperature, max_tokens)`。内部双路径：LangChain 可用时用 `ChatOpenAI.with_structured_output()` 做结构化输出；否则回退到原生 `OpenAI` client 调用 `response_format={"type": "json_object"}`。将 Pydantic schema 作为 JSON Schema 传给模型，返回解析后的 dict。多模型支持通过环境变量切换 base_url 和 api_key 实现，无需改代码。所有 LLM 调用（翻译、抽取、问题生成、报告生成）统一经过此网关，便于全局控制 temperature、max_tokens 等参数。

---

### ▸ prompts/ — 提示词管理层

#### registry.py — 提示词注册表

定义六种提示词的键名映射（product_translation / review_translation / review_cleanup / review_extraction / question_generation / report_generation ）和两种变体（main 英文 / CN 中文）。变体通过环境变量 `PROMPT_VARIANT` 选择并支持多别名（如 "zh"、"zh-cn"、"CN" 均指向中文变体）。`PROMPT_VARIANT_ALIASES` 字典包含 `"default" → "main"`，未设置时默认走英文。`_load_prompt()` 从变体子目录读取 `.md` 文件内容作为系统提示词，与 `USER_PROMPT_TEMPLATES` 中对应的用户提示词合并为 `ChatPromptTemplate`。对外暴露 `get_prompt()`（系统+用户完整模板）、`get_prompt_template()`（仅系统提示词对象）和 `get_prompt_variant()`（当前变体名）三个查询函数。

#### main/ 与 CN/ — 提示词变体目录

各含 6 个 Markdown 文件：`1_商品信息翻译`（将商品名、描述、品类翻译为英文并输出 JSON）、`2_评论翻译`（将批外文评论译为英文）、`3_评论清洗`（去除噪声、标准化表达）、`4_评论结构化抽取`（从评论中提取方面、情感极性、证据摘要）、`5_核验问题生成`（为每个方面生成可在商品信息中验证的问题）、`6_VOC报告生成`（基于聚合证据生成有归因的结构化报告）。变体间内容对应但语言不同，按 `PROMPT_VARIANT` 环境变量自动切换到对应语言。

#### dashboard.html / .css / .js — 工作流进度仪表盘

### ▸ schemas/ — Pydantic 数据模式

#### analysis.py — 分析模式（最大 schema 文件）

定义分析流程中的全部数据结构，包括：`ProductAnalysisRequest/Response`（分析请求和响应）、`RetrievalQuestion`（检索问题，含 intent 类型和生成方式）、`RetrievalRecord`（每次检索的记录，含文本/图片/混合路线的证据列表）、`ProductAnalysisReport`（最终报告，含 strengths/weaknesses/controversies/evidence_gaps/suggestions 五大段落）、`ClaimAttribution`（每条洞察的来源追溯，含 support_status/support_type/supporting_evidence 等字段）、`InsightItem`（单项洞察，含标签、摘要、置信度和支持证据）、`ImprovementSuggestion`（改进建议，含建议文本、归因、优先级）、`AspectAggregate`（聚合后的方面摘要）、`RetrievalQualityMetrics`（单题检索质量指标）。此外还有 ExperimentConfig、AnalysisMode、QuestionIntent 等枚举和辅助类型。文件长达 423 行，是整个系统数据模型的核心。

#### dataset.py — 数据集模式

定义数据集层的标准结构：`ProductEvidencePackage`（单商品完整证据包，含标准化后的文本块、图片、图片区域和评论记录，所有元素都有稳定 ID）、`TextEvidence`（一段商品文本及其元数据）、`ImageEvidence`（一张商品图片及合成的默认区域）、`ImageRegion`（图片的矩形区域，作为视觉证据单元）、`ReviewRecord`（标准化后的单条评论）、`DatasetOverview/DatasetNormalizeRequest/NormalizationResult` 等扫描和标准化的输入输出结构。

#### index.py — 索引模式

定义索引相关结构：`IndexedEvidence`（索引化的证据条目，包含路由类型、嵌入向量、元数据、产品归属）、`ProductIndexSnapshot`（单产品索引快照，含商品 ID、文本/图片证据数量、时间戳）、`IndexBuildRequest/Response`（索引构建的请求参数和结果统计）。

#### review.py — 评论模式

定义评论相关的输入输出：`ReviewInput`（原始评论数据）、`PreprocessedReview`（清洗后的评论）、`ReviewAspect`（从评论中抽取的单个方面，含方面名/情感/置信度/证据摘要）、`ReviewExtractionRequest/Response`（抽取请求和响应，含 LLM/heuristic 模式标记）、`ReviewSamplingPlan`（采样计划，各项权重和目标数量）。

#### question_cache.py — 问题缓存模式

定义问题生成缓存的签名和负载：签名为 prompt_digest + aspect_count + model_name 的哈希组合，负载为缓存的 QuestionIntent 和 RetrievalQuestion 列表。用于跨运行复用问题生成结果，避免对同一组 aspect 重复调用 LLM。

#### retrieval_cache.py — 检索缓存模式

定义检索缓存的两种签名/负载：`QueryEmbeddingCacheSignature/Payload` 对查询文本嵌入的缓存（按文本哈希命中），`RerankCacheSignature/Payload` 对重排序结果的缓存（按 query+候选集指纹命中）。两个缓存都由 `retrieval_cache_service.py` 管理，以 JSON 文件持久化到 `02_outputs/` 下。

### ▸ stage1_dataset/ — Stage 1: 数据标准化

#### dataset_service.py — 数据集服务

### ▸ stage2_review_modeling/ — Stage 2: 评论建模

#### review_service.py — 评论抽取服务

完成评论的预处理和信息抽取：先通过关键词密度和文本长度过滤低信号评论（如纯好评 "great!" 类），再对剩余评论调用 LLM 做方面抽取（主路径）或回退到关键词匹配的启发式方法（降级路径）。抽取结果包含方面名、情感极性、置信度和证据摘要。支持缓存到 `02_outputs/2_aspects/` 并可在后续任务中复用缓存。同时维护抽取模式标记（LLM / heuristic_no_llm / fallback_heuristic）。依赖 `ReviewSamplingService` 做采样控制，依赖 `ReviewDeduplicationService` 做结果去重。

#### review_sampling_service.py — 评论采样服务

从 `03_configs/review_sampling_profiles.json` 加载三种采样策略（problem_first 偏重低分、balanced 均匀分布、praise_first 偏重高分），将总的评论配额按权重分配给 1-5 各星级。支持通过环境变量或参数指定策略名称，运行时根据商品的实际星级分布执行加权随机采样。确保大数据量下分析的评分代表性。

#### deduplication_service.py — 去重服务

对 `ReviewAspect` 列表按 `(review_id, aspect, sentiment, evidence_span)` 四元组做去重。逻辑简单但关键：未去重的重复方面会直接导致 LLM 上游的 prompt 膨胀、报告重复和归因失准。22 行实现体现了精准定位复用点的设计哲学。

### ▸ stage3_retrieval/ — Stage 3: 多模态检索

#### embedding_service.py — 向量嵌入服务

多后端文本和图像嵌入的统一入口，支持四种路径：(1) 远程 DashScope text-embedding-v4 API、(2) 本地 Qwen3-Embedding-0.6B（HuggingFace Transformers 加载）、(3) CLIP ViT-B/32 图像嵌入、(4) 确定性哈希 embedding 作为无 LLM 降级方案。文本向量统一投射到 64 维 float 列表，图像向量同理。内部集成了 LRU 查询缓存（最多 256 条），并可直接落盘缓存到 `retrieval_cache_service`。对每个嵌入请求先用签名查缓存，命中则直接返回，显著减少 API 调费和推理时间。

#### index_backends.py — 索引后端抽象

定义了 `IndexBackend` 抽象基类（含 save_snapshots / load_snapshots / search / index_exists / index_location 五个方法）以及两个实现：`LocalJsonBackend` 将所有嵌入向量和元数据序列化为 JSON 文件，搜索用内存余弦相似度；`QdrantBackend` 将数据写入本地 Qdrant 向量数据库，搜索通过 Qdrant 的 cosine distance 查询并可按 product_id 过滤。后端选择由环境变量 `retrieval_backend` 控制，`create_index_backend()` 工厂函数根据配置创建实例，保证了 Pipeline 层代码与具体后端解耦。

#### index_service.py — 索引编排服务

整合 `DatasetService`、`EmbeddingService` 和 `IndexBackend`，对外提供 `build_index()` 方法。流程：加载标准化证据包 → 遍历所有文本块/图片/图片区域 → 调用 EmbeddingService 生成向量 → 组装 `IndexedEvidence` 条目 → 批量写入后端。同时生成 `ProductIndexSnapshot` 包含商品维度的统计摘要。支持品类过滤、产品过滤和增量构建。此服务是检索前必须执行的初始化步骤。

#### local_model_utils.py — 本地模型加载工具

封装了 Qwen3 系列三个小参数模型的加载和推理：`LocalEmbeddingModel`（Qwen3-Embedding-0.6B，提取 last_hidden_state 作为向量）、`LocalRerankerModel`（Qwen3-Reranker-0.6B，用因果 LM head 打分）、`LocalMultimodalRerankerModel`（Qwen3-VL-2B-Instruct，接收文本+图片做多模态相关性判断）。全部支持 `resolve_device()` 自动检测 XPU（Intel GPU）/CUDA/CPU 优先级。每个模型类都使用 `@lru_cache` 实现单例，避免重复加载。

#### retrieval_service.py — 检索编排服务

为每个 `RetrievalQuestion` 执行双路检索：文本路（查询商品描述等文本证据）和图像路（查询商品图片和合成区域）。每条路线先通过 `IndexBackend.search()` 召回 Top-k 候选，再调用 `RerankerService` 重排序，最后合并为 `RetrievedEvidence` 列表。支持消融实验条件控制：`ablation_no_image_route` 关闭图像路，`ablation_no_reranking` 跳过重排序。内部有逐问题的进度上报机制，确保长时间运行的 UI 反馈。

#### reranker_service.py — 重排序服务

对检索召回的候选证据集执行两阶段重排序：文本候选通过 DashScope text-rerank API 或本地 Qwen3-Reranker-0.6B 做语义相关性评分；图像候选通过 Qwen-VL-Max（远程）或 Qwen3-VL-2B-Instruct（本地）做多模态相关性判断（给候选图片和问题文本，输出 0-1 相关性分数）。支持逐题缓存到硬盘。不在配置的实验条件下也可走确定性启发式重排（关键词匹配打分）作为降级方案，确保 `--no-llm` 模式仍可输出合理的排序结果。

#### retrieval_cache_service.py — 检索缓存服务

为 `EmbeddingService` 和 `RerankerService` 提供跨运行持久化的 JSON 缓存层。两种缓存模式：查询嵌入缓存（键为文本哈希，值为 64 维向量列表），重排缓存（键为 query+candidates 的组合签名，值为排序后的候选 ID 序列和分数字典）。缓存文件按品类/产品维度拆分存储在 `02_outputs/3_indexes/` 下，支持手动逐出和过期检测。

#### openvino_integrated.py / openvino_models.py — OpenVINO 推理后端

提供基于 Intel OpenVINO 的加速推理路径。`openvino_integrated.py` 封装了 `OVModelForFeatureExtraction` 和 `OVModelForCausalLM` 的加载与推理，支持 Intel XPU（GPU）和 NPU；`openvino_models.py` 在此基础上封装为与标准服务接口兼容的 `OpenVINOEmbeddingModel`、`OpenVINORerankerModel`、`OpenVINOMultimodalRerankerModel`，使 Pipeline 层可无感知地在 PyTorch 和 OpenVINO 间切换。主要用于在 Intel 硬件上降低推理延迟和内存占用，属于可选加速路径。

### ▸ stage4_generation/ — Stage 4: 报告生成

#### analysis_service.py — 分析编排服务（3045 行，全系统最大文件）

`ProductAnalysisService` 是整个 Pipeline 第四阶段的总编排器，负责将前三阶段产物（标准化证据包、方面列表、检索记录）通过 LLM 导向最终的分析报告。核心流程：(1) 方面聚合——将多个 review 中相似方面归并、计算置信度和争议信号；(2) 问题规划——调用 `QuestionGenerationService` 为每个聚合方面生成证据验证问题；(3) 证据检索——调用 `RetrievalService` 执行双路查询；(4) 报告生成——将聚合方面、检索证据、商品上下文组合为 prompt，通过 LLM 生成结构化报告（主路径）或拼接 heuristic 报告（降级）；(5) 归因标注——为报告中的每条 insight 和 suggestion 标注其支撑证据（review 引用、商品文本块 ID、图片 ID），输出 `ClaimAttribution` 列表；(6) 报告精炼——调用 `ReportRefinementService` 去重、校准和归因分类；(7) 产物体积——写入报告 JSON、回放侧车、HTML 和 RunManifest。支持断点续跑（checkpoint 机制，以签名哈希判定输入是否变化）和消融控制（可独立关闭问题规划/图片路线/重排序/归因）。

#### question_service.py — 问题生成服务

接收方面列表，为每个方面生成可验证的检索问题。LLM 路径会将方面列表序列化为 JSON payload 填充入预约模板，要求模型输出 `QuestionIntent`（包含问题文本、意图类型和预期证据类型）列表。降级路径用模板化规则生成固定句式的问题（如 "What does the product description say about {aspect}?"）。输出包含问题意图（internal planning）和问题（用于检索）两个粒度，前者有更细的 route 建议，后者是实际的检索查询文本。同时有缓存层，对相同方面组合避免重复 LLM 调用。

#### question_cache_service.py — 问题缓存服务

很薄的一层（41 行），将问题生成缓存逻辑封装为 `QuestionGenerationCacheService`。签名为方面列表的 prompt digest + aspect 数量 + 模型配置的哈希组合；负载为对应该签名的问题意图和问题列表。缓存文件存储在 `02_outputs/3_indexes/` 下，加载路径硬编码但可接受。

#### report_refinement_service.py — 报告精炼服务

对 LLM 生成的原始报告做后处理：(1) 去重——通过标签+摘要文本指纹去重 insights 和通过建议文本指纹去重 suggestions；(2) 归因分类——将每条 insight 标注为 product-related/content-related/expectation-related；(3) 摘要校准——对每条 insight 生成简洁的校准摘要；(4) 证据合并——将分散在多个 insight 上的 support evidence 按层级聚合为报告级的 summary evidence 和 review evidence。此服务在无 LLM 模式下也会运行，确保不同执行条件下的输出结构一致。

#### html_export_service.py — HTML 导出服务

将 `ProductAnalysisReport` + artifact bundle（序列化 JSON + 图片路径 + 检索记录等）渲染为单文件自包含 HTML 报告。支持中/英双语标签切换（通过 `get_prompt_variant()` 判断语言），生成的内容包括：产品概览卡、优势/问题/争议/证据缺口各段落的卡片式展示、证据画廊（可展开的商品图片缩略图）、检索质检摘要（路线级覆盖率和精排分数）、运行配置快照、"过程抽屉"（展开可见各阶段耗时统计）。输出为内嵌 CSS 和 JS 的完整 HTML 文件，不依赖外部资源，适合离线分享和论文截图。

#### artifact_sidecar_service.py — 产物侧车服务

为每次分析运行生成两种 "sidecar" JSON：(1) 反馈侧车（feedback sidecar），预置空反馈结构供后续人工标注或模型二次调用时填入——可对每条 insight 标注是否正确、证据是否充分；(2) 回放侧车（replay sidecar），记录此次运行的完整输入摘要（aspect 摘要、问题列表、检索 key、LLM 参数等），用来在后续 session 中精准恢复分析上下文。这两种 sidecar 都支持从已有文件加载（场景：第二次运行加载上次的反馈并据此调整报告），是项目的审计友好性设计的核心体现。

### ▸ workflows/ — 工作流编排

#### single_product_workflow.py — LangGraph 单产品工作流

用 LangGraph `StateGraph` 构建 4 节点流水线：overview_node（数据集概况）→ normalize_node（标准化证据包）→ index_node（构建向量索引）→ analyze_node（评论抽取+问题规划+检索+报告生成）。节点间用 `SingleProductWorkflowState` TypedDict 传递状态。内置 `InMemorySaver` checkpoint 机制，支持从任意阶段中断后恢复。编译后的 graph 对外暴露 `.invoke()` 和 `.stream()` 两种执行方式。此文件是 CLIG 入口 `run_workflow.py` 和 API 端点 `/analysis/product` 共用的编排核心。

#### experiment_runner.py — 实验矩阵运行器

CLI 驱动的批量实验运行引擎。输入参数：品类列表、每品类产品数、最大评论数、输出目录。为每个产品 × 每个实验条件（8 种：full_system + 4 种消融 + 3 种对照）逐一调用 `ProductAnalysisService` 执行完整 Pipeline，结果以 JSONL 追加写入 `experiment_log.jsonl`。支持 `--resume` 断点续跑：检查已有记录跳过已完成的（产品, 条件）组合。内置 `EXPERIMENT_PROGRESS_PLAN` 定义了阶段级进度计划，与 `WorkflowProgressReporter` 联动。

#### control_experiments.py — 对照实验基线

实现了三种外部系统方法的忠实再现：(1) Lewis 2020 "标准 RAG"：将所有检索到的证据文本拼接为 context 一次性输入 LLM 生成报告；(2) JARVIS 证据图：将检索结果按证据类型构建图结构，再让 LLM 从图中推理出属性和矛盾；(3) VeriCite 三阶段引用验证：先生成报告摘要 → 再逐条回溯证据做一致性检查 → 最后标注引用支撑度。三个对照组均使用 `QwenChatGateway` 调用相同的 LLM，只在 prompt 结构和证据组装逻辑上不同，确保变量控制。

#### llm_judge_evaluation.py — LLM-as-Judge 评估器

读取 `experiment_log.jsonl`，对每种实验条件 × 每个产品执行 LLM 评判。评估三个维度：(1) 检索质量（检索到的证据与问题的相关性 1-5 分）；(2) 报告覆盖率（报告对方面列表的覆盖度 1-5 分）；(3) 事实一致性（报告内容与给定证据之间的一致性 1-5 分）。评估时 LLM 会收到问题和被评审的输出（如报告段、归因列表），并被请求输出结构化评分。结果写入 `evaluation_log.jsonl` 并生成 `evaluation_summary.json`（按条件聚合的均值对比）。评估过程支持断点续跑。

### ▸ 独立文件

#### runtime_progress.py — 运行时进度上报器（987 行）

`WorkflowProgressReporter` 用一个树状状态机记录工作流执行的每一层进度：Module（阶段，如 normalize/index/analyze）→ Step（步骤）→ Count（计数型子步骤，如"已处理 8/30 条评论"）。提供 `start_count_step/advance_step/complete_step/complete_module` 四个核心操作，以及 `use_workflow_progress()` 上下文管理器用于自动开始和结束。内部将状态持久化为 JSON 文件，供 HTML 仪表盘轮询读取实现实时 UI。支持多模块并发报告（通过模块/步骤名隔离），是所有长流程的统一进度数据源。

### 脚本与入口层

#### run_workflow.py — 主流程 CLI 入口（469 行）

项目最核心的用户入口，通过 argparse 提供约 20 个命令行参数：`--category` / `--product-id` 指定目标商品，`--cn` 切换中文数据集，`--no-llm` 禁用 LLM 走启发式路径，`--resume-from-aspects` / `--resume-from-analysis-checkpoint` 从中间产物恢复，`--export-html` 和 `--write-manifest` 控制输出类型，`--R_5` 等多种快捷标志覆盖采样策略和 Top-k 设置。脚本在导入核心包前先覆盖环境变量（如设置 `PROMPT_VARIANT=CN`），然后调用 `build_single_product_workflow().invoke()` 驱动完整执行。最终生成 `WorkflowExecutionSummary` 并可选写出 RunManifest JSON。

### 配置与文档

#### 03_configs/review_sampling_profiles.json — 评论采样策略

定义了 `problem_first`（差评优先）、`balanced`（均衡采样）、`praise_first`（好评优先）三种策略的各星级抽取权重比，例如 `problem_first` 对 1-2 星的权重远高于 4-5 星。这些权重直接驱动 `ReviewSamplingService` 的配额分配。

#### 03_configs/runtime_execution_policy.json — 运行时执行策略

两个布尔开关：`allow_degradation` 控制 LLM API 失败时是否静默降级为 heuristic；`full_power` 控制是否强制所有模型后端可用且 LLM 不可禁用。正式实验时一般设为 `allow_degradation=false` 避免静默 fallback 污染结果，日常开发时设为 `true` 以保持可用性。
