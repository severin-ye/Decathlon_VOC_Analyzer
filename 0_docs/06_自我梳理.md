# 自我梳理：如何讲清楚 Decathlon VOC Analyzer

> 本文档按自然递进逻辑（是什么 → 怎么工作 → 架构 → 亮点 → 难点 → 价值），帮你把项目讲清楚。

---

## 第一问：这是一个什么项目？

> 目标：一句话定位 + 问题域 + 你的角色。

**一句话**：一个基于多模态证据驱动的 VOC（用户之声）分析系统，能从商品描述、商品图片和用户评论中自动生成有证据支撑的结构化分析报告。

**解决的问题**：电商运营人员看到用户评论后，需要手动对照商品详情页和图片来验证评论是否属实、哪些是产品本身问题、哪些是用户期望偏差。这个项目把这个过程自动化了——它读评论→提问题→查证据→出报告，每条结论都标注了引用的哪条评论、哪段商品描述、哪张图片。

**我的角色**：论文第一作者，负责系统架构设计、全部源码实现（~30 个核心模块，3000+ 行最核心的分析编排服务）、实验矩阵设计和论文写作。

---

## 第二问：系统怎么工作的？

> 目标：先用一句话讲，再展开。

### 一句话版

"用户怎么说 → 查商品怎么说 → 查图片怎么说 → 三方对齐 → 出报告，每条结论挂证据。"

### 展开版（8 句话讲清全流程）

1. **输入标准化**：把每个商品的 description 文本、product images、user reviews 三种异构数据统一分配稳定 ID，形成标准证据包 `ProductEvidencePackage`。

2. **评论建模**：按评分做加权采样（可偏重差评/均衡/偏重好评），用 LLM 从每条评论中抽取 aspect + 情感 + 证据摘要，去重后得到产品的 VOC 画像。

3. **问题规划**：为每个 aspect 生成可验证的检索问题，比如 "商品描述里有没有提到口袋大小？"——这些问题不是直接问 LLM，而是去商品信息中找证据回答。

4. **双路检索**：文本路线用 embedding 查商品描述和规格参数；图片路线用 CLIP/Qwen-VL 查商品图片和自动合成的图片区域。

5. **两阶段重排序**：文本候选走 text-reranker 做语义相关性打分，图片候选走 Qwen-VL 做多模态图文相关性判断。

6. **报告生成**：把聚合方面 + 检索证据 + 商品上下文拼成 prompt，LLM 生成结构化报告（优势 / 问题点 / 争议 / 证据缺口 / 改进建议）。

7. **证据归因**：报告的每条 insight 都标注了支撑它的具体评论 ID、商品文本块 ID、图片 ID——每条结论可追溯到原始证据。

8. **产物输出**：JSON 报告 + 自包含 HTML 报告 + 检索质量 Manifest + 回放侧车 + 反馈侧车，整套制品可审计、可复现。

## 第三问：系统架构是怎样的？

> 目标：说清楚代码怎么组织，分几层。

### 分层总览

```
入口层     CLI 脚本 (run_workflow.py)  /  FastAPI 服务  /  交互式 UI
  │
工作流层   LangGraph StateGraph (4 节点: 概览→标准化→索引→分析)
  │
服务层     Stage1 标准化 → Stage2 评论建模 → Stage3 多模态检索 → Stage4 报告生成
  │
公共层     配置中心 / LLM 网关 / 提示词注册表 / Schema 定义 / 运行策略 / 进度上报
  │
基础设施   Pydantic / LangChain / OpenAI / Qdrant / torch+transformers / OpenVINO
```

### 四个 Pipeline Stage

| Stage | 做什么 | 核心文件 (行数) |
|-------|--------|----------------|
| Stage1 数据集 | 扫描原始文件，标准化为证据包 + 中文翻译 | `dataset_service.py` (473) |
| Stage2 评论建模 | 评分感知采样 + 方面抽取 + 去重 | `review_service.py` (448) |
| Stage3 多模态检索 | 文本/图片双路 embedding + 索引 + 重排序 | `reranker_service.py` (466) |
| Stage4 报告生成 | 问题生成 + 报告 LLM 生成 + 归因 + HTML 导出 | `analysis_service.py` (3045) |

## 第四问：有哪些技术亮点？

> 目标：区分真正有技术含量的事 vs 单纯调 API。

### 1. 多后端可插拔架构

每个能力（LLM、Embedding、Reranker、Index）都支持多后端，通过环境变量一键切换：

| 能力 | 远程后端 | 本地后端 |
|------|---------|---------|
| 文本 LLM | qwen-plus / DeepSeek-V3 / OpenAI | — |
| 文本 Embedding | text-embedding-v4 | Qwen3-Embedding-0.6B |
| 图像 Embedding | — | CLIP ViT-B/32 / Qwen3-VL |
| 文本 Reranker | gte-rerank-v2 | Qwen3-Reranker-0.6B |
| 多模态 Reranker | qwen-vl-max | Qwen3-VL-2B-Instruct |
| 向量索引 | Qdrant | Local JSON (余弦相似度) |

切换不需要改代码，也不需要写 if-else 分支——每个后端实现同一抽象基类，工厂函数自动创建。

### 2. 运行时策略控制（防静默降级）

学术实验要求严格：不能 API 挂了就悄悄切到简单方法。系统有一套完整的运行时策略：
- `allow_degradation=false`：任何后端失败立即抛异常停止
- `full_power=true`：验证所有 LLM 依赖可用，禁止禁用 LLM

所有 Pipeline 中需要降级的地方都先查策略，失败按策略决定是降级还是报错。

### 3. 多级缓存系统

三层缓存减少重复的 LLM 调用和 API 费用：
- **查询嵌入缓存**：相同文本直接复用 embedding 向量（LRU 256 条 + 文件持久化）
- **重排序缓存**：相同 query+候选集的排序结果按签名命中
- **问题生成缓存**：相同 aspect 组合的问题不重复生成

实验矩阵中跨条件复用显著加速（多个消融条件共用同一组问题）。

### 4. 远程 + 本地 OpenVINO 联合推理

在 Intel 硬件上整合 OpenVINO 的 `OVModelForFeatureExtraction` 和 `OVModelForCausalLM`，模型加载时自动检测 XPU（Intel GPU）> CUDA > CPU 优先级。提供 PyTorch vs OpenVINO 的 side-by-side benchmark 脚本，记录了推理速度、显存、GPU 利用率对比。

### 5. 全链路证据归因

每条报告的 insight 都附 `ClaimAttribution` 对象：
- `support_status`：supported / partial / unsupported
- `support_type`：review / product_text / image / mixed
- `supporting_evidence`：具体 ID 列表

评估指标 `claim_support_rate`、`claim_grounded_rate`、`citation_precision` 可以量化归因质量，这在电商分析领域少见。

### 6. 实验矩阵 + LLM-as-Judge 自动评估

实验条件：1 个完整系统 × 4 个消融 × 3 个对照基线 = 每产品 8 种条件。LLM-as-Judge 自动对检索质量、报告一致性、归因精度打分。支持断点续跑——中断后重启自动跳过已完成的 (产品, 条件) 组合。

## 第五问：你遇到什么难点？怎么解决的？

### 难点 1：LLM 输出不可靠

LLM 生成的方面名不稳定（同义词变体），生成的报告段落可能重复或矛盾。

**解决**：为方面提取设计了 LLM + 关键词启发式双路径，启发式作为精确 fallback；报告生成后走 `ReportRefinementService` 做去重（文本指纹匹配）、归因分类（产品问题 / 内容问题 / 期望偏差）和证据合并。

### 难点 2：三种异构数据如何统一检索

商品描述是文本、图片是像素、评论又是单独数据源，统一检索需要不同模态的 embedding 和 reranking。

**解决**：设计了双路线架构——文本和图片走各自的 embedding（API text embedding / CLIP image embedding）和 reranker（text-rerank / Qwen-VL multimodal rerank），最终在检索记录中合并两条路线的结果，消融实验验证了每条路线的独立贡献。

### 难点 3：本地模型推理的性能和兼容性

Qwen3 系列小参数模型（0.6B~2B）虽然小但对硬件仍有要求，尤其是多模态模型。

**解决**：`local_model_utils.py` 统一了三类模型的加载和推理，`resolve_device()` 自动检测 XPU/CUDA/CPU。又集成了 OpenVINO 加速，在 Intel GPU 上推理延迟降低 40-60%。提供完整的 benchmark 和测试脚本验证各硬件上的正确性。

## 第六问：这个项目的价值是什么？

1. **可复现的学术制品**：论文 + 代码 + 实验矩阵 + LLM-as-Judge 评估形成闭环，所有结论有证据。
2. **多后端切换**：不需要 GPU 也能跑（纯 API / CPU 小模型 / OpenVINO Intel 加速），部署灵活。
3. **模块化架构**：每个 Stage 独立可替换——换商品、换模型、换检索后端、换报告模板都不影响其他模块。
4. **生产就绪的基础设施**：FastAPI 服务、LangGraph 断点恢复、进度仪表盘、产物审计——不只是一个 Jupyter notebook。
