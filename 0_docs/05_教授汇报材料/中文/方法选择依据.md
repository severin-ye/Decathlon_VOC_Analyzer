# 方法选择依据说明

---

## 1. 研究动机

### 问题背景

电商 VOC（Voice of Customer）分析面临的核心矛盾：

- **用户评论**包含主观使用体验（"太小了"、"质量很好"）
- **商品页面**包含客观证据（规格参数、产品图片）
- **现有工具**通常只分析评论文本，无法将主观意见与客观证据对齐

**具体场景**：
- 用户抱怨"容量太小" → 现有工具只记录"负面评价"
- 我们不知道：商品描述是否标明了容量？图片是否展示了内部空间？这个问题是产品缺陷还是用户期望偏差？

### 为什么需要新方法

| 现有方法 | 局限性 | 本系统回应 |
|-------------------|-------------|------------------------|
| 简单情感分类 | 只输出正面/负面标签，无法追溯原因 | 提取方面并追溯具体证据 |
| LLM 直接摘要 | 生成流畅文本但无法验证 | 证据约束生成，每个 claim 绑定证据 |
| ABSA | 只输出 (方面, 情感) 对，不检查商品证据 | 交叉验证：用商品证据支持或纠正评论意见 |
| 标准 RAG | 单文本路径，无多模态 | 双路检索：文本+图像独立召回 |

## 2. 方法选择依据

### 2.1 为什么选择四阶段流水线

**替代方案**：单阶段 LLM 直接输入所有数据生成报告

**为什么不选**：
- 输入数据量大（评论+描述+图片），超出 LLM 上下文窗口
- 无法追溯：不知道结论来自哪条评论、哪个证据
- 无法调试：出错时不知道哪个环节出问题
- 无法复现：每次运行结果不同

**本系统方案**：四阶段分离流水线

| 阶段 | 作用 | 为什么分离 |
|-----------|-----------|------------------------|
| Stage 1 标准化 | 统一证据格式 | 确保后续阶段有稳定的 ID 追踪基础 |
| Stage 2 评论建模 | 提取结构化方面 | 从非结构化评论中提炼可检索的需求信号 |
| Stage 3 多模态检索 | 检索商品证据 | 将需求信号与商品证据对齐 |
| Stage 4 报告生成 | 结构化输出 | 证据约束下生成可追溯的报告 |

**核心设计原则**：不是"让 LLM 做所有事"，而是"让 LLM 做它擅长的事（理解和生成），用结构化流程做它需要的事（检索和验证）

---

### 2.2 为什么选择问题导向检索

**替代方案**：直接用评论句子做检索查询

**为什么不选**：
- 评论句子表达不稳定：同一问题可以有多种表述（"太小了"、"放不下"、"容量不够"）
- 检索意图不明确：不知道要检索文本证据还是图像证据
- 检索结果与报告 claim 的关联不清晰

**本系统方案**：问题规划（Question Planning）

将每个评论方面分解为三种证据意图：
1. **文本支持**：商品描述/规格是否支持该意见？
2. **视觉确认**：商品图片是否展示相关特征？
3. **跨模态解析**：文本和图像解释是否一致？

**优势**：
- 检索意图明确：每个问题都有清晰的证据类型目标
- 检索与报告的关联清晰：问题→检索结果→claim 全链路可追溯
- 支持消融分析：可以单独移除某种问题类型验证其必要性

---

### 2.3 为什么选择双路独立检索

**替代方案**：将所有模态（文本+图像）嵌入同一向量空间混合检索

**为什么不选**：
- 文本和图像的语义空间不同，强行混合会导致匹配错误
- 图像证据（外观、结构、颜色）无法通过文本查询有效检索
- 无法独立评估文本路径和图像路径各自的贡献

**本系统方案**：
- **文本路径**：用文本嵌入检索商品描述、规格文本
- **图像路径**：用 CLIP 嵌入检索商品图片
- **独立召回后合并**：通过跨模态一致性约束结合，而非在向量空间混合

**优势**：
- 避免模态污染：文本查询不会检索到不相关的图像
- 可独立消融：可以关闭图像路径验证视觉证据的贡献
- 支持证据归因：每个 claim 可以标注来自文本还是图像证据

---

### 2.4 为什么选择证据约束生成

**替代方案**：开放式文本生成（让 LLM 自由写报告）

**为什么不选**：
- LLM 可能编造不存在的事实（幻觉）
- 无法验证每个结论是否有证据支持
- 输出格式不固定，难以评估和比较

**本系统方案**：
- **Schema 约束**：输出必须符合 Pydantic 模型定义（strengths/weaknesses/controversies/evidence_gaps/suggestions）
- **证据绑定**：每个 claim 必须关联到具体证据对象
- **证据空白处理**：找不到证据的 claim 标记为 `evidence_gap`，不强行编造

**优势**：
- 输出结构化：便于自动化评估和审计
- 幻觉控制：通过证据约束减少编造
- 可追溯：每个 claim 可追溯到具体证据

---

### 2.5 为什么使用 RAG 而非 Fine-tuning

| 维度 | Fine-tuning | RAG (本系统) |
|-----------|-------------|--------------|
| 数据需求 | 需要大量标注数据 | 利用已有商品数据 |
| 通用性 | 领域专用，换品类需重新训练 | 通用，换品类只需换数据 |
| 可解释性 | 黑盒，无法解释为什么生成这个结论 | 白盒，每个结论都有证据 |
| 更新成本 | 模型重训练 | 只需更新索引 |
| 当前适用性 | 项目数据量不足以有效 fine-tune | 适合数据量小但需要证据可追溯的场景 |

**本系统定位**：
- **当前版本**：使用 RAG + 结构化输出约束，零样本/少样本推理
- **Fine-tuning 作为未来方向**：在 `0_docs/01_设计文档/07-实施路线/高价值改进-论文.md` 中记录为后续改进方向
- **Ensemble 作为未来方向**：当前使用单一流水线，多模型集成在改进计划中

## 3. 各模块为什么选这个技术

### 3.1 LangGraph 工作流编排

**为什么选 LangGraph**：
- 需要明确的阶段依赖关系（Stage 1 → 2 → 3 → 4）
- 需要支持断点续跑和中间产物缓存
- 相比简单脚本，LangGraph 提供了状态管理和可视化能力
- 但当前版本实际上主要使用函数调用而非完整 LangGraph 图（在改进计划中）

**为什么不选其他框架**：
- Airflow / Prefect：太重，不适合研究原型
- 纯脚本：缺乏状态管理和可复现性

---

### 3.2 Pydantic Schema 约束

**为什么选 Pydantic**：
- Python 原生支持，与 FastAPI 无缝集成
- 运行时类型检查，确保输出格式正确
- 自动生成 JSON Schema，便于 API 文档和前端集成
- 支持嵌套模型，适合复杂结构化报告

**约束的价值**：
- 输出不是自由文本，而是结构化对象
- 每个字段都有类型约束，减少格式错误
- 便于下游评估和审计

---

### 3.3 Qdrant / 本地 JSON 索引

**为什么支持两种后端**：
- **本地 JSON 索引**：零依赖，适合快速验证和演示
- **Qdrant**：生产级向量数据库，支持高维嵌入和相似度搜索
- 可通过配置切换，无需修改代码

---

### 3.4 CLIP + text-embedding 双嵌入

**为什么选 CLIP（图像）**：
- 预训练模型，无需领域数据微调
- 支持图像-文本对比学习，适合商品图片检索
- 开源可用，无 API 费用

**为什么选 text-embedding-v4（文本）**：
- 中文支持好，适合商品描述和评论文本
- 通过 API 调用，无需本地部署
- 可切换到本地 Qwen3-Embedding 模型

---

## 4. 未使用技术的说明

### 4.1 Fine-tuning

**状态**：未在当前版本中使用

**原因**：
- 项目数据量（~200 商品，~33K 评论）不足以有效微调大语言模型
- 研究重点在于验证"证据驱动多模态分析"的架构可行性，而非追求 SOTA 性能
- 微调需要大量计算资源和时间，超出当前项目范围

**未来方向**：
- 方面提取器微调：用领域数据微调 aspect extraction 模型
- 重排序器微调：用标注数据微调 reranker 模型
- 在 `0_docs/01_设计文档/07-实施路线/高价值改进-论文.md` 中记录

---

### 4.2 Ensemble

**状态**：未在当前版本中使用

**原因**：
- 当前重点是建立可复现的单一流水线基线
- 集成多个模型会增加复杂性和资源消耗
- 研究阶段更适合先验证单模型架构，再考虑集成

**未来方向**：
- 多检索器集成：集成多个 embedding 模型的检索结果
- 多生成器集成：集成多个 LLM 的生成结果
- 在 `0_docs/01_设计文档/07-实施路线/高价值改进-论文.md` 中记录

---

### 4.3 端到端训练

**状态**：未使用

**原因**：
- 四阶段流水线中每个阶段使用不同模型（LLM、嵌入模型、重排序模型）
- 端到端训练需要统一损失函数和梯度回传，与当前模块化设计冲突
- 当前设计允许独立替换和升级每个模块

## 5. 方法局限性

| 局限性 | 说明 | 应对 |
|-------------|-----------|-----------|
| 图像证据粒度粗 | 使用整张图片和规则区域，非语义分割 | 记录为改进方向，当前阶段功能验证优先 |
| LLM 幻觉 | 即使 evidence 约束，LLM 仍可能编造 | 通过 schema 约束和归因机制降低风险 |
| 无人工标注 benchmark | 当前结果为系统验证，非 frozen benchmark | 设计可复现实验矩阵，支持增量评估 |
| 数据版权 | 商品图片和评论来自电商平台 | 仅用于研究，不重新分发 |

---

## 6. 总结

本系统的核心方法论选择基于以下原则：

1. **可追溯优于端到端**：四阶段分离流水线虽然复杂，但提供了全链路可追溯能力
2. **证据约束优于自由生成**：结构化输出和证据绑定虽然限制了灵活性，但提高了可信度
3. **RAG 优于 Fine-tuning**：在数据量有限的情况下，检索增强比模型微调更实用
4. **双路优于单路**：文本和图像独立检索虽然增加了复杂度，但避免了模态污染
5. **问题规划优于直接查询**：将方面分解为证据意图虽然增加了步骤，但提高了检索精准度
