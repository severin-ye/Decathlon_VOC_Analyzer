# 방법 선택 근거 설명

---

## 1. 연구 동기

### 문제 배경

전자상거래 VOC(Voice of Customer) 분석이 직면한 핵심 모순:
- **사용자 리뷰**는 주관적 사용 경험 포함 ("너무 작다", "품질이 좋다")
- **상품 페이지**는 객관적 증거 포함 (규격 파라미터, 제품 이미지)
- **기존 도구**는 대체로 리뷰 텍스트만 분석하고, 주관적 의견과 객관적 증거를 정렬하지 못함

### 왜 새로운 방법이 필요한가

| 기존 방법 | 한계 | 본 시스템의 대응 |
|---|---|---|
| 단순 감성 분류 | 긍정/부정 라벨만 출력, 원인 추적 불가 | 측면 추출 및 구체적 증거 추적 |
| LLM 직접 요약 | 유창한 텍스트 생성하나 검증 불가 | 증거 제약 생성, 각 claim 증거 바인딩 |
| ABSA | (측면, 감성) 쌍만 출력, 상품 증거 미검증 | 교차 검증: 상품 증거로 리뷰 의견 지지 또는 수정 |
| 표준 RAG | 단일 텍스트 경로, 멀티모달 없음 | 듀얼 경로 검색: 텍스트+이미지 독립 회수 |

## 2. 방법 선택 근거

### 2.1 왜 4단계 파이프라인인가

**대안**: 단일 단계 LLM이 모든 데이터를 직접 입력하여 보고서 생성

**선택하지 않은 이유**:
- 입력 데이터량이 많음 (리뷰+설명+이미지), LLM 컨텍스트 윈도우 초과
- 추적 불가: 결론이 어떤 리뷰, 어떤 증거에서 나왔는지 알 수 없음
- 디버깅 불가: 오류 발생 시 어느 단계에서 문제가 발생했는지 알 수 없음
- 재현 불가: 매 실행 결과가 다름

**본 시스템 방안**: 4단계 분리 파이프라인

| 단계 | 역할 | 왜 분리하는가 |
|---|---|---|
| Stage 1 표준화 | 통일 증거 포맷 | 후속 단계가 안정적인 ID 추적 기반을 가질 수 있도록 보장 |
| Stage 2 리뷰 모델링 | 구조화된 측면 추출 | 비구조화 리뷰에서 검색 가능한 요구 신호를 정제 |
| Stage 3 멀티모달 검색 | 상품 증거 검색 | 요구 신호와 상품 증거를 정렬 |
| Stage 4 보고서 생성 | 구조화 출력 | 증거 제약 하에 추적 가능한 보고서 생성 |

**핵심 설계 원칙**: "LLM이 모든 것을 하게 하지 않고", "LLM이 잘하는 일(이해와 생성)은 LLM에게, 구조화된 흐름이 필요한 일(검색과 검증)은 파이프라인에게"

---

### 2.2 왜 질문 기반 검색인가

**대안**: 리뷰 문장을 직접 검색 쿼리로 사용

**선택하지 않은 이유**:
- 리뷰 문장 표현이 불안정: 동일한 문제가 다양한 표현을 가질 수 있음 ("너무 작다", "안 들어간다", "용량 부족")
- 검색 의도가 불명확: 텍스트 증거를 검색할지 이미지 증거를 검색할지 알 수 없음
- 검색 결과와 보고서 claim의 연관성이 불분명

**본 시스템 방안**: 질문 계획 (Question Planning)

각 리뷰 측면을 세 가지 증거 의도로 분해:
1. **텍스트 지지**: 상품 설명/규격이 해당 의견을 지지하는가?
2. **시각 확인**: 상품 이미지가 관련 특징을 보여주는가?
3. **크로스모달 해석**: 텍스트와 이미지 해석이 일치하는가?

**장점**:
- 검색 의도 명확: 각 질문에 명확한 증거 유형 목표가 있음
- 검색과 보고서 연관성 명확: 질문→검색 결과→claim 전체 링크 추적 가능
- 소거 분석 지원: 특정 질문 유형을 개별적으로 제거하여 필요성 검증 가능

---

### 2.3 왜 듀얼 경로 독립 검색인가

**대안**: 모든 모달리티(텍스트+이미지)를 동일 벡터 공간에 임베딩하여 혼합 검색

**선택하지 않은 이유**:
- 텍스트와 이미지의 의미 공간이 다륾, 강제 혼합은 매칭 오류를 유발
- 이미지 증거(외관, 구조, 색상)는 텍스트 쿼리로 효과적으로 검색 불가
- 텍스트 경로와 이미지 경로의 개별 기여도를 독립적으로 평가 불가

**본 시스템 방안**:
- **텍스트 경로**: 텍스트 임베딩으로 상품 설명, 규격 텍스트 검색
- **이미지 경로**: CLIP 임베딩으로 상품 이미지 검색
- **독립 회수 후 병합**: 벡터 공간 혼합이 아닌 크로스모달 일관성 제약으로 결합

**장점**:
- 모달리티 오염 방지: 텍스트 쿼리가 관련 없는 이미지를 검색하지 않음
- 독립 소거 가능: 이미지 경로를 닫고 시각 증거 기여도 검증 가능
- 증거 귀속 지원: 각 claim이 텍스트 증거인지 이미지 증거인지 표시 가능

---

### 2.4 왜 증거 제약 생성인가

**대안**: 개방형 텍스트 생성 (LLM이 자유롭게 보고서 작성)

**선택하지 않은 이유**:
- LLM이 존재하지 않는 사실을 지어낼 수 있음 (환각)
- 각 결론에 증거 지원이 있는지 검증 불가
- 출력 형식이 고정되지 않아 평가 및 비교 어려움

**본 시스템 방안**:
- **Schema 제약**: 출력이 Pydantic 모델 정의를 준수해야 함 (strengths/weaknesses/controversies/evidence_gaps/suggestions)
- **증거 바인딩**: 각 claim이 구체적 증거 객체와 연결되어야 함
- **증거 공백 처리**: 증거를 찾을 수 없는 claim은 `evidence_gap`으로 표시, 강제로 지어내지 않음

**장점**:
- 출력 구조화: 자동화 평가 및 감사에 용이
- 환각 제어: 증거 제약으로 지어냄 감소
- 추적 가능: 각 claim이 구체적 증거로 추적 가능

---

### 2.5 왜 Fine-tuning이 아닌 RAG인가

| 차원 | Fine-tuning | RAG (본 시스템) |
|---|---|---|
| 데이터 요구 | 대량의 주석 데이터 필요 | 기존 상품 데이터 활용 |
| 범용성 | 도메인 전용, 카테고리 변경 시 재학습 필요 | 범용, 카테고리 변경 시 데이터만 교체 |
| 설명 가능성 | 블랙박스, 결론 생성 이유 설명 불가 | 화이트박스, 모든 결론에 증거 있음 |
| 업데이트 비용 | 모델 재학습 | 인덱스만 업데이트 |
| 현재 적합성 | 프로젝트 데이터량으로는 효과적 fine-tuning 불가 | 데이터량이 적지만 증거 추적이 필요한 상황에 적합 |

**본 시스템 위치**:
- **현재 버전**: RAG + 구조화 출력 제약, 제로샷/퓨샷 추론
- **Fine-tuning 향후 방향**: `0_docs/01_설계문서/07-실시로선/고가치개선-논문.md`에 후속 개선 방향으로 기록
- **Ensemble 향후 방향**: 현재 단일 파이프라인 사용, 다중 모델 통합은 개선 계획에 있음

## 3. 모듈별 기술 선택 근거

### 3.1 LangGraph 워크플로우 오케스트레이션

**LangGraph 선택 이유**:
- 명확한 단계 의존 관계 필요 (Stage 1 → 2 → 3 → 4)
- 중단점 재실행 및 중간 산출물 캐싱 지원 필요
- 단순 스크립트 대비 LangGraph가 상태 관리 및 시각화 기능 제공
- 하지만 현재 버전은 실제로 함수 호출 위주이며 완전한 LangGraph 그래프는 아님 (개선 계획에 있음)

**다른 프레임워크 미선택 이유**:
- Airflow / Prefect: 너무 무거워 연구 프로토타입에 부적합
- 순수 스크립트: 상태 관리 및 재현성 부족

---

### 3.2 Pydantic Schema 제약

**Pydantic 선택 이유**:
- Python 네이티브 지원, FastAPI와 원활한 통합
- 런타임 타입 검사, 출력 형식 정확성 보장
- JSON Schema 자동 생성, API 문서 및 프론트엔드 통합 용이
- 중첩 모델 지원, 복잡한 구조화 보고서에 적합

**제약의 가치**:
- 출력이 자유 텍스트가 아닌 구조화 객체
- 각 필드에 타입 제약이 있어 형식 오류 감소
- 하류 평가 및 감사에 용이

---

### 3.3 Qdrant / 로컬 JSON 인덱스

**두 가지 백엔드 지원 이유**:
- **로컬 JSON 인덱스**: 제로 의존성, 빠른 검증 및 데모에 적합
- **Qdrant**: 프로덕션급 벡터 데이터베이스, 고차원 임베딩 및 유사도 검색 지원
- 설정으로 전환 가능, 코드 수정 불필요

---

### 3.4 CLIP + 텍스트 임베딩 듀얼 임베딩

**CLIP(이미지) 선택 이유**:
- 사전 학습 모델, 도메인 데이터 미세 조정 불필요
- 이미지-텍스트 대비 학습 지원, 상품 이미지 검색에 적합
- 오픈소스 사용 가능, API 비용 없음

**text-embedding-v4(텍스트) 선택 이유**:
- 한국어 지원 우수, 상품 설명 및 리뷰 텍스트에 적합
- API 호출 방식, 로컬 배포 불필요
- 로컬 Qwen3-Embedding 모델로 전환 가능

---

## 4. 미사용 기술 설명

### 4.1 파인튜닝

**상태**: 현재 버전에서 미사용

**이유**:
- 프로젝트 데이터량 (~200 상품, ~33K 리뷰)이 대규모 언어 모델을 효과적으로 미세 조정하기에 부족
- 연구 목표는 "증거 기반 다중모달 분석" 아키텍처 타당성 검증이며 SOTA 성능 추구가 아님
- 미세 조정에는 대량의 계산 자원과 시간 필요, 현재 프로젝트 범위 초과

**향후 방향**:
- 측면 추출기 미세 조정: 도메인 데이터로 aspect extraction 모델 미세 조정
- 재순위 모델 미세 조정: 주석 데이터로 reranker 모델 미세 조정
- `0_docs/01_설계문서/07-실시로선/고가치개선-논문.md`에 기록

---

### 4.2 앙상블

**상태**: 현재 버전에서 미사용

**이유**:
- 현재 목표는 재현 가능한 단일 파이프라인 기준선 수립
- 다중 모델 통합은 복잡성 및 자원 소비 증가
- 연구 단계에서는 단일 모델 아키텍처 검증 후 통합 고려이 적합

**향후 방향**:
- 다중 검색기 통합: 다중 임베딩 모델의 검색 결과 통합
- 다중 생성기 통합: 다중 LLM의 생성 결과 통합
- `0_docs/01_설계문서/07-실시로선/고가치개선-논문.md`에 기록

---

### 4.3 엔드투엔드 학습

**상태**: 미사용

**이유**:
- 4단계 파이프라인의 각 단계가 다른 모델 사용 (LLM, 임베딩 모델, 재순위 모델)
- 엔드투엔드 학습에는 통일 손실 함수 및 그래디언트 역전파 필요, 현재 모듈화 설계와 충돌
- 현재 설계는 각 모듈을 독립적으로 교체 및 업그레이드 가능

---

## 5. 방법의 한계

| 한계 | 설명 | 대응 |
|---|---|---|
| 이미지 증거 입자도 거침 | 전체 이미지와 규칙 영역 사용, 의미론적 분할 아님 | 개선 방향으로 기록, 현재 단계는 기능 검증 우선 |
| LLM 환각 | 증거 제약이 있어도 LLM이 억지로 생성할 수 있음 | schema 제약과 귀속 메커니즘으로 위험 감소 |
| 무인공 주석 benchmark | 현재 결과는 시스템 검증, 고정 benchmark 아님 | 재현 가능한 실험 매트릭스 설계, 증분 평가 지원 |
| 데이터 저작권 | 상품 이미지와 리뷰는 전자상거래 플랫폼 출처 | 연구용만 사용, 재배포하지 않음 |

---

## 6. 요약

본 시스템의 핵심 방법론 선택은 다음 원칙에 기반합니다:

1. **추적 가능성 > 엔드투엔드**: 4단계 분리 파이프라인은 복잡하지만 전 경로 추적 가능성을 제공
2. **증거 제약 > 자유 생성**: 구조화 출력과 증거 바인딩은 유연성을 제한하지만 신뢰도를 향상
3. **RAG > Fine-tuning**: 데이터량이 제한된 상황에서 검색 증강이 모델 미세 조정보다 실용적
4. **듀얼 경로 > 단일 경로**: 텍스트와 이미지 독립 검색은 복잡도를 증가시키지만 모달리티 오염을 방지
5. **질문 계획 > 직접 쿼리**: 측면을 증거 의도로 분해는 단계를 증가시키지만 검색 정확도를 향상
